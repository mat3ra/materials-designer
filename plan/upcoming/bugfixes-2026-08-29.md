# Upcoming bugfixes — 2026-08-29

Three items found while reviewing the UX chain (PRs #285–#297) that were deliberately not
fixed there: two are larger than a review follow-up should carry unilaterally, and one is a
small correctness gap worth doing on its own. Ordered by what they cost the user.

---

## 1. A refresh loses the whole session

**Severity:** high — silent, total data loss on an action users take casually.

Nothing about the session survives a reload. `MaterialsDesignerContainer` holds every
material in a `useRef` plus `useState` history, and the only thing written to storage
anywhere in `src/` is the panel widths:

```
src/MaterialsDesigner.jsx:49   window.localStorage.getItem(PANE_SIZES_STORAGE_KEY)
src/MaterialsDesigner.jsx:101  window.localStorage.setItem(PANE_SIZES_STORAGE_KEY, …)
```

So an hour of building supercells, surfaces and transformations disappears on a stray Cmd+R,
a crashed tab, or a laptop sleeping badly. There is no warning and no recovery. Users have
no reason to expect this: the app looks like a document editor, and document editors do not
lose documents.

**Shape of the fix**

- Autosave `{ materials, index }` to `localStorage` on a debounce (~1s idle) — not the undo
  history, which is session-scoped and would balloon the payload.
- On load, if a saved session exists, restore it and say so: a dismissible bar reading
  *"Restored your last session · Start fresh"*. Restoring silently is worse than not
  restoring — a user who expected the default Si and got someone else's 400-atom slab will
  assume the app is broken.
- Key the entry by a schema version so a future `MDMaterial` change can invalidate old
  payloads instead of throwing on rehydrate.
- Stamp `originalSignature` on restore exactly as `MaterialsDesignerContainer` does for
  `initialMaterials`, or every restored material comes back marked as edited.
- Guard the size. `localStorage` caps around 5 MB per origin and a large supercell serialises
  big; on quota failure, drop the save and leave the session in memory rather than half-write.
- Skip autosave entirely when the host passes `initialMaterials` (the web-app embed owns
  persistence in that case) — otherwise MD would fight its own container for authority.

**Not this:** IndexedDB. The payload is one JSON blob read once at startup; the extra
machinery buys nothing until we want per-material history or attachments.

**Verify:** Cypress — create a material, reload the page, assert it is still there and the
restore notice appears; dismiss with "Start fresh" and assert the default material is back.

## 2. Renaming a material back does not clear the "edited" marker

**Severity:** low — cosmetic, but it undermines a signal the chain just added.

`syncUpdatedIndexBySignature` exists so that undoing an edit by hand clears the amber dot:
it recomputes the material's signature and compares it against the one stamped when the
material entered the session. `getMaterialSignature` deliberately folds the name in, because
`material.hash` covers only basis and lattice.

But the rename path never calls it:

```ts
// src/reducers/Material.ts
export function materialsUpdateNameForOne(state, action) {
    …
    return addUpdatedIndices({ ...state, materials }, [action.index]);  // ← unconditional
}
```

So renaming "Si" to "Si2" and back leaves the dot lit, while making the same round trip
through the basis editor clears it. The two paths disagree about what "edited" means.

**Fix:** swap `addUpdatedIndices(…, [action.index])` for
`syncUpdatedIndexBySignature(…, action.index)`, matching `materialsUpdateOne`. Two lines.

**Verify:** extend `tests/cypress/e2e/materials-list/updated-marker.feature` — rename a
material, assert the dot; rename it back, assert the dot is gone.

## 3. `shouldComponentUpdate` compares props with `JSON.stringify`

**Severity:** medium — a latent trap that has already produced one shipped bug.

```jsx
// src/MaterialsDesigner.jsx
shouldComponentUpdate(nextProps, nextState) {
    const [nextProps_, thisProps_, nextState_, thisState_] =
        [nextProps, this.props, nextState, this.state].map(JSON.stringify);
    return !(nextProps_ === thisProps_) || !(nextState_ === thisState_);
}
```

`JSON.stringify` drops functions. Every callback prop — `onUndo`, `onRedo`, `onUpdate`,
`onItemClick`, all of them — is therefore invisible to this comparison. A render whose *only*
change is a corrected callback is skipped, and the child keeps calling a stale closure.

This is not hypothetical. It is precisely why redo-by-keyboard stayed broken in #287 after
the obvious fix: two setters produced two renders, and the render carrying the corrected
`redo` closure was dropped here. The workaround was to collapse `past` and `future` into one
piece of state so a single render carries a consistent pair of callbacks. That works, but it
constrains how `useUndoableState` may be written forever, and the same trap waits for the
next prop that is a function.

Two further costs: `JSON.stringify` on the full material array runs on **every** render and
calls `toJSON()` on each material (which is why the whole thing is wrapped in a `try/catch` —
a Standata entry that fails schema validation would otherwise white-screen the app); and
non-serialisable values silently compare equal.

**Shape of the fix**

- Make every callback stable — most already are, via `useCallback(…, [])` in the container —
  then replace the whole method with a shallow prop/state comparison (`React.PureComponent`,
  or an explicit `shallowEqual`).
- `mdState` is replaced wholesale on each change, so a shallow compare catches real updates
  and stops re-rendering on identity churn alone.
- Audit for props built inline in `MaterialsDesigner.render` (object and array literals,
  arrow functions) — those defeat a shallow compare and need hoisting or memoising.
- Landing this should let `useUndoableState` split `past`/`future` again if that ever reads
  better, since the constraint was never about history semantics.

**Verify:** the existing `toolbar/keyboard-shortcuts.feature` and
`toolbar/control-availability.feature` already pin the behaviour the old comparison broke;
they must stay green. Watch the 3D canvas for re-render regressions — the pane is expensive
and was the reason for a bail-out check in the first place.

## 4. `npm run lint` never looks at a single `.jsx` file

**Severity:** medium — not a bug itself, but the reason bugs go unseen. Found while porting the
UX chain's new files to TypeScript, which turned linting *on* for them for the first time and
immediately surfaced a shipped `ReferenceError`.

`npm run lint` is `eslint src`. Given a directory, ESLint 7 lints `.js` plus any extension
matched by an `overrides[].files` pattern. The shared `@mat3ra/eslint-config` declares exactly
one override, `files: ["*.ts", "*.tsx"]`. Nothing matches `*.jsx`, so those files are skipped
outright. Measured on this tree:

```
$ npx eslint src -f json | …count by extension
{'ts': 5, 'tsx': 16, 'js': 8}   total 29
```

Twenty-five `.jsx` files — 4,626 lines, the majority of `src` — are never linted. Neither is
the husky pre-commit hook's `eslint src --fix`, which runs the same command.

What that hid, concretely: `HeaderMenuToolbar.jsx` calls `new MDMaterial(config)` while its
import sat commented out, so importing a material from Standata through the command palette
threw `ReferenceError: MDMaterial is not defined`. Plain `no-undef` would have caught it on the
commit that introduced it. (Fixed, with a Cypress regression test, in this branch.)

**Fix:** `eslint src --ext .js,.jsx,.ts,.tsx` in both `lint` and `lint:fix`. Note `lint-staged`
already scopes to `*.{js,jsx}` and passes explicit file paths, which bypasses the directory
default — so staged files *were* linted on commit, but only the ones being committed, and only
when husky ran.

**Expect fallout.** On the current tree the flip is nearly clean — the remaining findings were
fixed in the same commit — but that is only true because the UX chain's own `.jsx` files were
just gone over by hand. Run it once before turning it on and triage what appears; some of it
will be `simple-import-sort` noise that `--fix` handles, and some will be real.

**Worth noting for the TS migration:** converting a file to `.tsx` is currently the only way it
starts being linted. That is an argument for doing both — but they are independent, and the
lint fix is a one-line change that covers all 25 files at once.
